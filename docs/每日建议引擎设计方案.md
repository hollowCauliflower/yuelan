# 每日建议引擎设计方案

> **实施状态（2026-11-19 更新）**
>
> - 本方案 P0–P5、A1–A7、B1–B6 已全部落地，模板共 **306 条**，校验脚本与 18 条单元测试全绿。
> - 建议正文、宜忌、依据、反馈、提醒联动、语气人格、里程碑、微习惯、心情打卡、节气节日、周期趋势均已接入两个每日建议弹窗与记录列表。
> - 数据库仍为 **v8**：`mood` 列直接并入 v8 建表语句，未上线阶段不为测试库单独抬版本；旧 v7 库在升级到 v8 时补齐该列。
> - 天气扩展维度（湿度 / 紫外线 / 空气质量 / 花粉）与新增信号标签、占位符已纳入校验脚本白名单。

## 1. 背景

### 1.1 改造前链路（历史背景）

```
周期参数 → generateRangeRecords() 逐天推算阶段
        → GenerateSuggestionHelper 按阶段从 4 个数组随机取 1 条
        → 写入 menstrual_record.suggestion
        → 每日建议弹窗 / 记录列表直接展示该字段
```

关键实现位置：

| 环节 | 位置 |
| --- | --- |
| 随机取文案 | `GenerateSuggestionHelper.getRandomPhaseAdvice()` |
| 文案池（共 13 条） | `res/values-zh-rCN/strings.xml` 中 `*_suggestions` 四个 array |
| 生成并写库 | `MenstrualCycleRecordDaoImpl.generateRangeRecords()`、`HomeFragment.initData()` |
| 补签时写死文案 | `DailySuggestionBottomSheet.generateSuggestionForPhase()`、`CalendarFragment`、`PhaseRangeEditor` |
| 展示 | `DailySuggestionBottomSheet`、`DailySuggestionDialog`、`RecordAdapter` |
| 已有的组合式提醒 | `WeatherSuggestionHelper`（阶段 × 天气，但未推广） |

### 1.2 问题拆解

| # | 问题 | 具体表现 |
| --- | --- | --- |
| P1 | 文案总量太小 | 13 条 ÷ 4 阶段，单个 28 天周期内必然重复多次 |
| P2 | 生成时机错误 | 生成预测记录时随机一次就冻结在库里，同一句会伴随用户一整天 |
| P3 | 维度单一 | 只吃"阶段"一个信号，流量、痛经、备注、天气、周期天数、历史规律全部闲置 |
| P4 | 无结构 | 一整段文字，没有"个性化开场 + 可执行动作 + 记录引导"的层次 |
| P5 | 预测与实际混同 | 用户实际记录也被写入同一套随机文案，与本人症状无关 |

> 结论：根因不是"文字不够多"，而是**建议只在错误的时间点、用单一维度、生成一次就固化**。

## 2. 设计目标与非目标

### 目标

1. **丰富**：同一阶段在不同日期、不同身体状态下给出不同内容，一个完整周期内不重复。
2. **人性化**：文案由"当天真实状态"驱动，包含具体数字（周期第 N 天、距离下次 D 天、痛经等级、气温）。
3. **可解释**：每条建议都能追溯到它是被哪个信号触发的，便于排查与后续调优。
4. **稳定**：同一天内反复打开，文案不跳变。
5. **零表结构变更**：不改数据库版本，不新增表，不破坏现有备份/导入逻辑。

### 非目标

- 不引入在线 LLM 生成（隐私、网络、成本、内容审核均不可控）。若将来需要，只作为"可选润色"，离线模板始终是主路径。
- 不改变阶段推算、周期分段、补签校验的既有逻辑（避免再次出现口径分裂）。
- 不做疾病诊断或用药推荐，文案仅限生活方式层面。

## 3. 总体架构

新增一个纯计算、无副作用的展示层引擎，替换"读库里的整段文字"这一种展示路径。

```
SuggestionSignals（信号层）
  ├─ 周期信号：阶段 / 周期第 N 天 / 阶段内第 k 天 / 距下次经期 D 天
  ├─ 身体信号：当天记录（流量等级、痛经等级、备注、是否已记录）
  ├─ 环境信号：今日天气、明日天气、季节、时段
  └─ 历史信号：平均周期长度、近 N 次痛经分布、连续打卡天数、规律性评分
        ↓
SuggestionContext（聚合为只读数据对象）
        ↓
SuggestionEngine（规则层）
  ├─ 候选收集：按插槽从模板池筛选可用片段
  ├─ 打分排序：命中信号的片段优先，其余按权重
  └─ 去重轮转：以日期为种子，保证同周期内不重复
        ↓
SuggestionContent（结构层）
  ├─ opening   开场：个性化定位
  ├─ focus     关注：针对当天身体的 1 条动作
  ├─ tip       贴士：阶段 × 环境
  └─ nudge     引导：记录 / 打卡
        ↓
UI 渲染（每日建议弹窗、记录列表预览）
```

要点：**引擎只读数据、不写库**；数据库 `suggestion` 字段降级为兜底与历史快照。

## 4. 信号层设计

### 4.1 周期信号

| 信号 | 计算方式 | 已具备的能力 |
| --- | --- | --- |
| 当前阶段 | `MenstrualRecord.getMenstrualCycle()`，无记录时按周期参数推算 | 已有 |
| 周期第 N 天 | `CycleCalculator.getDayInCurrentCycle(startTime, totalCycleDay)` | 已有 |
| 阶段内第 k 天 | 当前日期 − 该阶段起始日 + 1，起始日由 `CycleCalculator.calculatePhaseDateRange()` 得出 | 已有 |
| 距下次经期 D 天 | `ReminderCycleHelper.nextPeriodStart()` 与今天做差 | 已有 |

> 阶段内第 k 天是"人性化"的关键：经期第 1 天与第 5 天、黄体早期与经前 3 天，身体感受完全不同，不应共用一套文案。

### 4.2 身体信号

数据源为当天 `MenstrualRecord`：

- `hasFlowData()` / `flowLevel`（少量 / 适中 / 过量）
- `hasPainData()` / `painLevel`（轻度 / 中度 / 严重 / 剧痛）
- `notes`、`flowNote`、`painNote`（可选，仅做关键词弱匹配，如"失眠""头痛""腰酸"）
- `isPrediction()`：区分"用户实际记录"与"系统预测"

规则优先级（强 → 弱）：

1. 痛经 ≥ 中度 → 输出热敷 / 休息 / 必要时就医提示
2. 流量"过量" → 输出观察是否异常增多的提示
3. 有备注命中关键词 → 输出对应主题的一句话
4. 仅有轻度症状 → 输出温和安抚
5. 无任何症状数据 → 不输出 focus 插槽，把篇幅让给 tip

### 4.3 环境信号

| 信号 | 数据来源 | 可用范围（重要约束） |
| --- | --- | --- |
| 今日/明日天气 | `OpenMeteoHelper.fetchWeatherForDate()` | 仅 `[今天-5, 今天+16]`，超出范围需降级 |
| 温度 | `Weather.getTemperature()`，复用 `WeatherSuggestionHelper.extractTemperature()` 的解析方式 | 同上 |
| 季节 | 由日期月份推导（春 3-5 / 夏 6-8 / 秋 9-11 / 冬 12-2） | 全时段可用 |
| 时段 | 由当前系统小时推导（早 / 日间 / 晚） | 仅"今天"有意义 |

降级规则：日期超出天气可用区间，或网络失败时，直接跳过天气相关片段，**不允许**因为天气缺失就退化成"无建议"。

### 4.4 历史信号

现有统计口径已内嵌在 `StatisticsFragment`（相邻经期间隔 ≥ 10 天切分轮次，完整周期数 = 轮次数 − 1，平均周期长度取轮次间隔均值）。引擎需要复用时，必须**把这段切分逻辑抽取为独立 Helper**，而不是在新引擎里重写一遍——否则会重现"统计页和日历口径不一致"的老问题。

可产出的信号：

- 平均周期长度、最长/最短周期（规律性评分：极差 ≤ 3 天为"很规律"，≤ 7 天为"较规律"，否则"波动较大"）
- 历史同期痛经分布（用于"你经期前几天常伴痛经"这类描述）
- 连续打卡天数（用于正向激励）

历史信号属于**低频信号**，建议只用于开场句或每周一次的特别文案，不建议天天出现，否则会显得说教。

## 5. 模板层设计

### 5.1 片段化，而非整段

每个阶段维护一个**片段池**，片段带标签，由引擎按插槽组装：

```json
{
  "id": "luteal_pre_period_rest",
  "slot": "tip",
  "phase": ["LUTE_PHASE"],
  "tags": ["pre_period_3d", "cold_weather"],
  "weight": 10,
  "template": "这几天容易疲惫，晚上早点收工，睡前泡个脚会舒服些。"
}
```

字段说明：

- `slot`：`opening` / `focus` / `tip` / `nudge`（插槽本身可扩展，后续可加 `insight` 依据、`action` 微行动，见第 12 章）
- `phase`：适用阶段
- `tags`：命中条件，与信号匹配
- `weight`：同条件候选的排序权重
- `template`：支持 `%1$d`（天数）、`%2$s`（阶段名）、`%3$s`（天气）等占位符

### 5.2 容量要求

| 阶段 | 片段数下限 | 说明 |
| --- | --- | --- |
| 经期 | 24 | 需覆盖第 1 天 / 第 2-3 天 / 末期三档 |
| 卵泡期 | 18 | 含"接近排卵"的过渡段 |
| 排卵期 | 14 | 需区分备孕意向（见 5.4） |
| 黄体期 | 24 | 需覆盖早期 / 中期 / 经前 3 天 |
| 通用 | 10 | 与阶段无关的睡眠、饮水、情绪类 |

设计基线合计约 90 条片段，可组合出远超 90 种不同输出；实际已扩到 **306 条**（含语气变体、里程碑、节气节日、心情/微习惯/天气扩展标签）。

### 5.3 去重与稳定性

这是本方案能否被用户感知为"丰富"的核心机制，必须同时满足两个看似矛盾的要求：

- **同一天内稳定**：同一天反复打开弹窗，内容不能变。
- **跨天不重复**：一个周期内不能反复看到同一句。

建议做法（"洗牌轮转"而非纯随机）：

1. 每个插槽的候选池按 `id` 排序后，用 `dateId` 做固定种子的洗牌，得到当天的确定顺序。
2. 取第 `(周期内天序号各插槽的偏移)` 条，而不是取随机第 0 条。
   - 等价实现：`index = Math.floorMod(seedFromDate + dayInCycle, poolSize)`。
3. 同一天多次调用，种子相同 → 结果必然相同。
4. 相邻两天 `dayInCycle` 递增 → 索引递增 → 天然错开。

> 禁止直接使用 `new Random().nextInt()`：这是当前 P2 问题的根源，既不可复现也无法保证跨天不撞。

### 5.4 语气与内容规范

- 单条建议总长度控制在 60-100 字，超过需要分行。
- 口吻统一为"平辈朋友"，避免"您应该""必须"。
- 不使用绝对化医疗断言（如"一定会""必须就医"），改为"如果持续加重，建议咨询医生"。
- 备孕意向：排卵期文案需中性，不能默认用户有备孕计划。可读取设置中是否开启备孕相关提醒来决定，未开启时使用中性表述。
- 每条文案必须至少含一个**具体动作**（热敷、补水、早睡、散步），不能只有形容词。

## 6. 数据库字段的定位调整

**`suggestion` 字段只做兜底，不改变既有展示结构；为支持心情打卡新增 `mood` 列，但不提升数据库版本（未上线阶段）。**

| 字段 | 现状 | 调整后 |
| --- | --- | --- |
| `menstrual_record.suggestion` | 唯一展示来源，写死 | 降级为**兜底/历史快照**：仅当引擎无法生成时回退展示 |
| `menstrual_record.mood` | 无 | 新增列（0 未记录 / 1 好 / 2 一般 / 3 低落），并入 v8 建表语句；旧 v7 库升级到 v8 时 `ALTER TABLE ... ADD COLUMN` |

好处：

- 备份/导入/导出逻辑完全不受影响（导出/导入已同步 mood、flow_note、pain_note）。
- 老版本升级上来的历史记录仍可展示。
- 未上线阶段不为测试库单独抬版本，避免无意义的版本自增；正式发布前如需为存量用户补列，再按项目约定升版本并逐级 ALTER。

同时需要**停止**在以下三处继续写入随机文案（改为写空或保留原值），避免继续制造不可信的静态数据：

- `MenstrualCycleRecordDaoImpl.generateRangeRecords()`
- `HomeFragment.initData()`
- `PhaseRangeEditor` 两处 `setSuggestion()`

> 若为降低风险希望保留写入，可先只改展示层，把"停止写入"放到第二阶段。两种顺序都可行，但必须写进实施计划，不能遗漏。

## 7. 界面呈现

### 7.1 建议卡片三段式

当前是单行文本，改为三行结构化展示（不改弹窗整体布局，仅把 `tv_suggestion` 拆成 2-3 个文本行 + 小标题，或在一个 TextView 内用换行 + 分隔符组织）：

```
【开场】经期第 2 天，距离下次预计还有 26 天。
【关注】今天痛经中度，可以热敷下腹 10 分钟，别硬扛。
【引导】记一笔今天的流量，下次预测会更准。
```

正文仍用一个 `tv_suggestion` 承载，但默认折叠到前 3 行：只有第 3 行真的被省略时才在下方显示「展开全文」，展开后按钮变「收起」，再收起回到首屏。判定基于 TextView 实际排版后的省略号（`layout.getEllipsisCount`），短建议不会出现多余按钮；文本重新生成（换一条、打卡、天气到达）后回到折叠态。折叠逻辑统一在 `widget/CollapsibleText.java`，居中弹窗与日历底部弹窗共用。

### 7.2 分场景差异

| 场景 | 处理 |
| --- | --- |
| 今天 + 有实际记录 | 四个插槽全开，focus 基于真实症状 |
| 今天 + 无记录（预测） | 输出 opening + tip + nudge，不编造症状 |
| 历史日期 | 只保留 opening + tip（天气可能已超出可用区间），不出现"记一笔"引导 |
| 未来日期 | 只输出 opening + tip 的预测语气，明确标注"预测" |

### 7.3 记录列表预览

`RecordAdapter` 当前截取 `suggestion` 前 20 字。改为从引擎取 `opening` 的短版本（或 `tip` 摘要），避免列表里出现大段文字被硬截断。

## 10. 验收标准

1. 同一日期反复打开每日建议弹窗 20 次，文案完全一致。
2. 连续 28 天（可造数据）打开，同一插槽无重复句。
3. 当天录入"痛经 严重"后重新打开弹窗，focus 插槽内容随之变化。
4. 断网状态下打开弹窗，不出现空白建议，天气行隐藏、建议正文完整。
5. 历史日期（超出天气可用区间）打开，能正常展示且不含天气类文案。
6. 补签 / 阶段修改 / 批量范围编辑三个入口保存后，日历、记录列表、每日建议三处文案口径一致。
7. 数据库版本号不变，旧数据升级后无异常。

## 11. 风险与注意事项

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 口径再次分裂 | 引擎若自行实现"阶段内第几天"，可能与日历/提醒不一致 | 一律复用 `CycleCalculator` 与 `ReminderCycleHelper`，禁止另起一套 |
| 统计逻辑抽取引入回归 | `StatisticsFragment` 的周期切分被多处依赖 | P0 单独作为一步，只搬不改，先验证数值一致 |

| 文案量膨胀导致维护困难 | 300+ 条片段散落在代码里 | 统一放 `assets/suggestion_templates.json`，按阶段分组，由校验脚本把关 |
| 内容质量 | 片段可组合后易出现语义重复（开场和 tip 都在说保暖） | 插槽间设互斥主题标记，同一主题在同一屏只出现一次 |

## 12. 丰富度扩展路线（可选增强）

先明确一个判断标准：「丰富」其实有三种，不能混为一谈，也不能用同一种手段解决。

| 类型 | 含义 | 本方案的覆盖情况 |
| --- | --- | --- |
| 内容广度 | 更多话题：睡眠、情绪、饮食、运动、就医提示 | 靠扩充片段池逐步覆盖 |
| 表达形式 | 卡片、宜忌、可展开依据、音频、微行动 | 靠界面分层实现 |
| 个性化深度 | 真的基于"你"的数据，而非"这个阶段" | 第 3-5 章已解决 |

下文按投入产出排序，均为可选项，不影响主方案落地。

### 12.1 低成本、高感知（建议纳入首期）

| 编号 | 增强 | 做法 | 复用的现有能力 |
| --- | --- | --- | --- |
| A1 | 今日三件事 | 首屏固定三行：身体 / 生活 / 心情各一条，而非混成一段 | 四个插槽已足够 |
| A2 | 每条建议可展开"为什么" | 点击后展开依据，如"因为今天痛经中度，且你近 3 次经期第 2 天都记录到痛经" | 当天记录 + 历史统计 |
| A3 | 今日宜 / 忌 | 两句短清单，如"宜：热敷、早睡 ｜ 忌：冰饮、熬夜" | 阶段 × 天气 |
| A4 | 语气人格可选 | 设置项：温柔 / 简洁 / 元气，同一片段存 3 个变体 | 纯文案，无新数据依赖 |
| A5 | 建议反馈 | 每条后加"有用 / 换一条"，换一条取候选下一条并记录偏好，用于调整 weight | 本地 SharedPreferences |
| A6 | 里程碑与纪念 | 连续记录 7/30 天、使用满 100 天、第 12 个周期等，当日追加一句 | 已有历史数据 |
| A7 | 提醒联动 | 当天有黄体酮/复查提醒时，nudge 改为"今天 19:00 记得按时服用" | 已有 `Reminder` 表 |

### 12.2 需要新增轻量数据（已实施）

| 编号 | 增强 | 说明 |
| --- | --- | --- |
| B1 | 心情一键打卡 | 三个文字按钮（好/一般/低落），不弹表单；写入 `menstrual_record.mood`，预测行会升级为实际记录 |
| B2 | 睡眠 / 饮水微习惯 | 建议卡片下方两个可勾选小目标，按日期存 SharedPreferences，并联动建议文案 |
| B3 | 天气维度扩展 | 湿度、紫外线、空气质量、花粉；空气质量独立接口，失败静默降级 |
| B4 | 节气与节日 | 二十四节气 + 公历节日 / 母亲节 / 父亲节；农历节日暂不做 |
| B5 | 品牌角色化 | 沿用月亮/鲸鱼视觉做叙述者（“月亮想对你说…”），形成人格一致性 |
| B6 | 周期趋势解读 | 用历史统计生成“你的周期比上个月短了 2 天”“近期波动较大，预测仅供参考” |

### 12.3 需要新功能立项（不在本方案范围）

- 基础体温 / 排卵试纸录入与排卵确认
- 呼吸引导、热敷计时等 1 分钟音频/动画引导
- 今日建议卡片分享（需先解决隐私脱敏）

### 12.4 重要原则：丰富 ≠ 首屏堆字

弹窗首屏必须控制在 3 行以内（约 60-100 字），其余内容一律折叠：

- 正文本身：超过 3 行只展示前 3 行，末尾「展开全文 / 收起」切换
- 点击展开：建议依据、阶段科普
- 二级入口：今日宜忌、本周主题

否则"丰富"会直接变成"信息过载"，打开率反而下降。这条原则优先级高于本章任何一条增强。

### 12.5 实际取舍（已全部实施）

首期原计划只做 A1 / A2 / A3 / A5 / A7，后续按产品要求把 **A4 / A6 与 B1–B6 全部补齐**：

- A4 语气人格、A6 里程碑属于纯文案/已有数据，不增加录入负担；
- B1 心情打卡新增 `mood` 列（并入 v8，不抬版本）；
- B2 睡眠/饮水使用 SharedPreferences 按日期存储，不进入数据库；
- B3 天气维度扩展在空气质量接口失败时静默降级；
- B4 节气节日使用纯日期算法，B5 品牌角色化复用现有月亮/鲸鱼视觉，B6 复用 `CycleStatsHelper` 的趋势口径。

## 13. AI 生成式方案（可选增强）

### 13.1 结论先行

可以做，但**不要让 AI 替换规则引擎**。AI 只适合做"上层增强"，本地引擎必须保留，负责首屏秒出、离线可用、失败兜底。否则一旦网络差或服务波动，每日建议这个每天必看的入口就会直接开天窗。

### 13.2 四种可选形态对比

| 形态 | 运行时成本 | 离线可用 | 延迟 | 个性化 | 隐私/合规 | 落地难度 |
| --- | --- | --- | --- | --- | --- | --- |
| 构建期 AI 写模板 → 人工审核 → 打进 assets | 0 | 可用 | 0 | 中（内容多样，但不针对个人） | 无 | 低 |
| 运行时在线生成（自建代理 → LLM） | 每次请求 | 不可用，需回退 | 2-5 秒 | 高（可结合当天症状） | 需授权 + 脱敏 + 备案 | 中高 |
| 端侧小模型（MediaPipe / llama.cpp） | 一次性下载 + 持续耗电 | 可用 | 1-10 秒（看机型） | 高 | 数据不出设备 | 高（包体/兼容性） |
| 远端模板包（AI 生成 → 审核 → 下发） | 极低 | 缓存后可用 | 0 | 中高 | 低 | 中 |

建议演进路径：**构建期生成 → 远端模板包 → 在线生成（可选开关）**。

另有一种交互形态：对话式"问一问"（如"今天能跑步吗？"），本质属于在线生成，需单独设计入口与上下文管理，不建议与每日建议同一期做。

### 13.3 若做在线生成，必须满足的 8 条工程约束

1. **密钥不进 APK**：必须经自建代理/云函数中转。当前项目直连 Open-Meteo 是因为它无需密钥，LLM 不能照抄这个模式。
2. **只发结构化信号，不发自由文本**：上送阶段、周期第 N 天、倒计时、痛经/流量等级、天气、季节；备注原文留在本地，最多上送本地提取的关键词标签。
3. **强制 JSON Schema**：`opening / focus / tip / nudge / insight` 五个字段，缺字段或解析失败一律判为失败。
4. **当天缓存**：缓存键 = `dateId + contextHash + 语气 + promptVersion`，同一天只请求一次。这同时解决了"文案跳变"和成本失控两个问题。
5. **先本地后 AI**：进入首页先渲染本地引擎结果，AI 返回后再替换，**绝不阻塞首屏**。
6. **超时与降级**：3 秒超时、最多重试 1 次，失败静默回退本地版本，不弹任何错误提示。
7. **版本化与灰度**：`promptVersion` 落库便于回滚；AI 开关支持按用户灰度。
8. **内容安全**：服务端过滤敏感词与医疗断言；客户端提供关闭开关与反馈入口。

### 13.4 输入输出示例

上送（脱敏后的结构信号）：

```json
{
  "phase": "LUTE_PHASE",
  "dayInCycle": 24,
  "daysToNextPeriod": 4,
  "painLevel": 2,
  "flowLevel": 0,
  "weather": { "text": "小雨", "temp": 12 },
  "season": "autumn",
  "history": { "avgCycle": 29, "regularity": "stable" },
  "tone": "gentle",
  "promptVersion": "v1"
}
```

返回（强制 schema，任一字段缺失即整体判失败）：

```json
{
  "opening": "黄体期第 5 天，距离下次预计还有 4 天。",
  "focus": "今天痛经中度，先热敷 10 分钟，别硬扛。",
  "tip": "外面在下小雨，注意腰腹保暖。",
  "nudge": "记一笔今天的感受，预测会更准。",
  "insight": "依据：你近 3 次经期前 4 天都记录到痛经。"
}
```

### 13.5 合规与成本（国内上架必看）

- 月经数据属于敏感个人信息，必须单独同意、隐私政策明示、可随时关闭；关闭后完全走本地引擎。
- 若使用境内生成式 AI 服务，需确认服务方已完成生成式人工智能服务备案；部分应用市场对"AI 生成内容"功能有额外说明要求，上架前需核实。
- 成本量级：每人每天 1 次、约 500 token 输入 / 150 token 输出，按国产主流模型价格约每人每月几分钱；用户量上来后必须限流与缓存。
- 文案与设置页需保留医疗免责声明，并遵守未成年人保护相关要求。

### 13.6 为什么不建议端侧模型

项目 `minSdk 24`，覆盖面很广。端侧 LLM 依赖 GPU/NPU 与 300MB 以上模型，中低端机和旧系统无法保证体验，包体与耗电也会明显上升。若将来要做，只能作为"可选下载增强包"，不能作为默认路径。

### 13.7 如果只做一件 AI 相关的事

推荐 **"AI 批量写模板 + 人工审核 + 打进 assets"**：

- 零运行时风险、零隐私风险、零网络依赖；
- 文案池可以从 90 条扩到上千条级别，多样性提升立竿见影；
- 与第 5 章的引擎完全兼容，不需要为 AI 单独改架构。

这是当前投入产出最高的一步，也是后续做在线生成的内容与评测基线。

## 14. AI 模板生产方案（已采用）

### 14.1 决策记录

- **采用** 13.7 的路线：AI 批量写模板 → 自动校验 → 人工审核 → 打进 `assets`。
- **不引入**运行时 AI 调用；在线生成作为后续可选能力，本期不做。
- 模板需覆盖第 12 章的 A1/A2/A3/A5/A7：三件事、依据、宜忌、反馈、提醒联动。

这样做的核心理由：AI 只参与**内容生产**，不参与运行时决策。用户端仍然是纯离线、零延迟、零隐私外发，而文案多样性可以提升一个数量级。

### 14.2 生产流水线

```
定义覆盖矩阵（14.4）
    → 按"阶段 × 主题"分批调用 LLM（14.5）
    → 自动校验脚本（14.6）：tools/suggestion_template_check.js
    → 人工抽检与改写（14.7）
    → 合并进 assets/suggestion_templates.json
    → 版本号 +1，随 APK 发版
```

工具链路沿用现有约定：`tools/` 目录下用 Node 脚本（与 `icon_packager.js` 一致），不进入 APK 包体。

### 14.3 片段 Schema（最终版）

在 5.1 的基础上补齐增强项所需字段：

```json
{
  "id": "luteal_pre_period_rest",
  "slot": "focus",
  "phase": ["LUTE_PHASE"],
  "tags": ["pre_period_3d", "pain_moderate"],
  "topic": "warmth",
  "tone": "gentle",
  "mutexGroup": "warmth",
  "weight": 10,
  "template": "今天痛经{{painText}}，先热敷 10 分钟，别硬扛。",
  "insight": "依据：你近 3 次经期前 4 天都记录到痛经。"
}
```

字段说明（仅列新增）：

| 字段 | 取值 | 作用 |
| --- | --- | --- |
| `topic` | `warmth` / `sleep` / `diet` / `exercise` / `mood` / `hygiene` / `medical` | 用于插槽间互斥，避免开场和贴士都在说保暖 |
| `tone` | `gentle` / `brief` / `cheerful` | 对应 12.1 A4，未启用时固定 `gentle` |
| `mutexGroup` | 同上主题 | 同一屏内同组只出现一次 |
| `insight` | 可空 | 对应 12.1 A2 的"为什么" |
| `template` 占位符 | `{{phaseName}}` `{{dayInCycle}}` `{{daysToNextPeriod}}` `{{painText}}` `{{flowText}}` `{{weatherText}}` `{{temp}}` `{{streak}}` `{{reminderTime}}` `{{reminderTitle}}` `{{usageDays}}` `{{cycleNo}}` `{{festivalName}}` `{{cycleDiff}}` | 只允许白名单，禁止自定义 |

新增两个插槽：`insight`（依据，对应 A2）与 `yiji`（宜忌，对应 A3）。宜忌片段格式固定为"宜：… ｜ 忌：…"，便于统一渲染。

**运行时加载与版本管理**

- `assets/suggestion_templates.json` 顶层含 `schemaVersion`、`contentVersion`、`templates` 三个字段。
- 解析失败或 `schemaVersion` 不匹配时，回退到代码内置的最小片段集（每阶段 2 条），保证永不空屏。
- 首期不做热更新，内容随 APK 发版，避免引入远端配置与灰度复杂度。
- 体积控制：1000 条约 200KB，对包体影响可忽略。

| focus | 161 | 四阶段 × 天段 + 通用主题 + 心情标签 + 花粉 |
| tip | 41 | 季节/天气/湿度/紫外线/空气质量/睡眠打卡 |
| nudge | 25 | 记录引导、提醒联动、微习惯、里程碑 |

| yiji | 17 | 阶段/天气/节日宜忌 |

| 阶段 | 天段 | 必覆盖主题 | 每格下限 |
| --- | --- | --- | --- |
| 经期 | 第 1 天 / 第 2-3 天 / 第 4 天起 | 保暖、休息、补水、卫生、痛经应对 | 2 |

矩阵必须由脚本校验覆盖率，缺格直接报错，不允许"大概写了一些"。

### 14.5 生成提示词规范

分批调用，每批 20 条，且**一批只生成一个"阶段 × 天段"组合**。一次性生成过多会明显拉低质量与去重效果。

系统提示词要点：

1. 角色：为月经健康类 App 撰写每日建议片段，口吻是"平辈朋友"，不是医生。
2. 禁止：医疗诊断、疗效承诺、绝对化表述（治愈、根治、一定、必须就医、疗程）。
3. 每条必须含**至少一个具体动作**（热敷、补水、早睡、散步、换卫生用品等）。
4. 单条 15-40 字；不使用 emoji；不使用"您"。
5. 必须输出严格 JSON 数组，字段与 14.3 完全一致，不得增删字段。
6. 占位符只能使用 14.3 白名单；没有对应信号时不得使用该占位符。
7. 同一批内不得出现语义重复的片段。

用户提示词示例：

```
阶段=黄体期，天段=经前3天，主题=情绪与睡眠，语气=gentle，生成 20 条。
可用的 tag 白名单：pre_period_3d、pain_mild、pain_moderate、cold_weather、rainy。
```

### 14.6 自动校验规则

`tools/suggestion_template_check.js` 必须全部通过，任一失败即中断：

1. JSON 合法，字段齐全，无多余字段。
2. `id` 全局唯一，命名符合 `阶段_主题_序号`。
3. `slot` / `tone` / `phase` / `topic` 均为枚举内取值。
4. 单片段长度 15-40 字；拼装后的整段长度 60-100 字。
5. 占位符只允许白名单，且每个占位符在 `tags` 中必须有对应信号来源。
6. 命中禁用词表（治愈 / 根治 / 一定 / 必须就医 / 包治 / 疗程 / 保证）即失败。
7. 必须命中动作词表（热敷 / 补水 / 早睡 / 散步 / 换 / 泡脚 / 拉伸 / 通风 等）。
8. 去重：与库内已有片段的 4-gram Jaccard 相似度 > 0.6 判为重复。
9. 覆盖率：14.4 矩阵每格 ≥ 2 条，缺格报错。
10. 每个 `mutexGroup` 内不得同时出现语义冲突的主题。

### 14.7 人工审核清单

- 是否存在事实性错误或伪科学表述？
- 是否隐含"用户一定有性生活/备孕计划"等假设？
- 痛经、流量异常相关文案是否给出正确的就医边界？

## 16. 运行时实现细节（已完成）

### 16.1 生成流程

```
界面层（两个每日建议弹窗 / 记录列表）
    → SuggestionContextHelper.build(...)
        周期：CycleCalculator / ReminderCycleHelper
        身体：当天记录（流量、痛经、mood）
        环境：Weather + 季节 + 节气/节日
        历史：CycleStatsHelper（规律性、连续记录、痛经趋势、周期趋势）
        里程碑：SuggestionMilestoneStore（首次使用日期、使用天数、周期序号）
        打卡：MicroHabitStore（睡眠、饮水）
        语气：SuggestionToneStore
    → SuggestionEngine.generate(context, templates, feedback, skippedIds)
    → SuggestionContent（opening / focus / tip / nudge / insight / yiji）
    → 弹窗正文三行 + 宜忌 + 可展开依据 + 反馈按钮 + 打卡区
```

引擎只读数据、不写库；`menstrual_record.suggestion` 仅作为模板异常时的兜底。

### 16.2 语气人格

- 取值：`gentle`（温柔，默认）/ `brief`（简洁）/ `cheerful`（元气）。
- 设置入口：设置页「每日建议 → 建议语气」，存入 `suggestion_tone` SharedPreferences。
- 选择规则：先按所选语气收集候选；若该语气没有可用模板，或温柔语气能命中**更具体的标签**（如痛经、天气、提醒），则回退温柔语气。
  这样语气只改变措辞，不会把“今天痛经中度”这类真正相关的建议挤掉。
- 已为核心插槽（opening / focus / tip / nudge）补充 brief / cheerful 变体；缺失时自动回退。

### 16.3 打卡数据

| 数据 | 落点 | 说明 |
| --- | --- | --- |
| 心情 | `menstrual_record.mood`（0/1/2/3） | 已有记录只更新 mood；预测行会升级为实际记录；无记录时用当天展示阶段创建最小记录 |
| 睡眠 / 饮水 | `micro_habit` SharedPreferences，键为 `sleep_yyyyMMdd` / `water_yyyyMMdd` | 不进入数据库与备份 |
| 首次使用日期 | `suggestion_milestone` SharedPreferences | 首次读取时以最早实际记录或今天为基准，之后固定 |
| 语气 | `suggestion_tone` SharedPreferences | 不影响周期数据 |
| 反馈分 | `suggestion_feedback` SharedPreferences | 限制在 ±50，避免单条文案霸屏 |

心情打卡入口在两个每日建议弹窗的卡片底部，仅在查看“今天”时出现。

### 16.4 新增标签与占位符

| 标签 | 命中条件 |
| --- | --- |
| `mood_good` / `mood_ok` / `mood_low` | 当天 mood = 1 / 2 / 3 |
| `sleep_done` / `water_done` | 当天对应微习惯已勾选 |
| `solar_term` / `festival` | 当天为节气 / 公历节日 |
| `milestone_usage` | 今天且使用天数命中 7/30/100/180/365 |
| `milestone_cycle` | 今天且第 3/6/12/24 个周期，且处于周期前三天 |
| `high_humidity` / `dry_air` | 湿度 ≥ 80% / ≤ 30% |
| `high_uv` | 紫外线指数 ≥ 7 |
| `poor_air` | 欧洲 AQI ≥ 100 |
| `high_pollen` | 花粉指数 > 0 |
| `cycle_shorter` / `cycle_longer` | 最近完整周期比此前均值短/长 ≥ 2 天 |

| 占位符 | 数据来源 |
| --- | --- |
| `{{usageDays}}` | 使用天数 |
| `{{cycleNo}}` | 当前记录周期序号 |
| `{{festivalName}}` | 节气 / 节日名称 |
| `{{cycleDiff}}` | 周期长度变化天数（渲染为绝对值） |

校验脚本 `suggestion_template_check.js` 已同步这些占位符与标签依赖：用了占位符却没声明对应标签会直接报错。

### 16.5 天气扩展与降级

- 预报接口追加 `uv_index_max` 与逐时 `relative_humidity_2m`（取目标日平均湿度）。
- 空气质量与花粉来自独立接口 `air-quality-api.open-meteo.com`，请求超时更短（2 秒连接 / 3 秒总超时）。
- **先回调基础天气，再异步补空气质量**：天气行不会因为空气质量接口慢而延迟；补到数据后再回调一次，用于刷新建议与缓存。
- 空气质量接口失败、日期超出范围或字段为空时，对应标签不命中，模板自动跳过，不影响正文。
- 缓存按“日期 + 地点”存储，扩展维度有值才写、无值则移除，避免跨日期残留。
- 仍遵守接口约束：`past_days` 与 `start_date/end_date` 不同时传。

### 16.6 节气与节日

- 二十四节气使用 21 世纪通用公式 `[Y×0.2422 + C] - int(Y/4)`，已用 2026 年官方日期校验（立春 2/4、春分 3/20、冬至 12/22）。
- 公历节日：元旦、情人节、妇女节、劳动节、儿童节、国庆、平安夜、圣诞；母亲节 / 父亲节按“第 n 个星期日”计算。
- 农历节日（春节、中秋等）不在本期范围，避免引入农历转换表。

### 16.8 已知边界

- 空气质量与花粉接口在中国大陆覆盖有限，通常只能拿到 AQI，花粉多为空值。

- 里程碑文案只在纪念节点当天出现，历史日期不补发。
- 微习惯只对“今天”生效，历史日期不读取当天打卡。
